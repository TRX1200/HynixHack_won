# 상황별 판단 카드

핵심 질문: **무엇이 답을 바꾸는가? 가장 싼 검증은 무엇인가? 남은 시간에 꼭 필요한가?**
아래는 일반 문제 해결 지침이며 특정 평가의 출제/채점 기준이 아닙니다.

## 처음 보는 과제
| 상황 | 내릴 판단 | 바로 할 행동 | 피할 행동 |
|---|---|---|---|
| 목표가 모호하다 | 코딩보다 목적/필수 산출물 확인이 먼저 | 사용자·입력·성공 기준을 정리하고 업무 담당자에게 질문 | 모든 요구를 AI가 추측하도록 둠 |
| 문서에 답이 이미 있다 | 담당자에게 같은 질문을 반복할 필요가 적다 | 원문 위치를 기록하고 적용조건만 확인 | 질문 수를 늘리기 위한 질문 |
| 기능 요구가 많다 | 필수와 선택을 분리한다 | 끝까지 작동하는 핵심 흐름 한 개부터 | 모든 화면/기능을 동시에 생성 |
| 데이터가 크다 | 전체를 LLM 문맥에 넣지 않는다 | 파일 목록·스키마·검색/집계부터 | 원본 전체를 매 응답마다 반복 |
| 설치가 막혔다 | 허용된 제공 도구로 축소하거나 신고 | 표준 라이브러리/수동 파일 읽기 대안 | 다른 경로로 차단 우회 |
| 시간 30분 이하 | 신규 구조 변경보다 제출 안정성 | 핵심 검사·실행법·한계·저장 점검 | 새 프레임워크/MCP 설치 |

## 이미지
| 상황 | 판단과 행동 |
|---|---|
| 기준 이미지와 위치가 다름 | 차이 마스크 전에 정렬 필요성을 확인. 위치 이동은 결함 근거가 아님 |
| 밝기만 다름 | 조명과 노출 차이를 점검. 임계값으로 불량률을 단정하지 않음 |
| 작은 결함 의심 | 원본 해상도의 crop 확인. 확대 보간은 새 정보를 만들지 않음 |
| 결함 정의가 없음 | 관찰/의심 후보와 합격·불합격을 분리. 판정 기준 질문 |
| 정답 라벨이 없음 | 정확도·재현율을 만들지 않음. 검토 범위와 미확정 표시 |
| 썸네일에서는 안 보임 | 썸네일만으로 정상 확정 금지 |
| 좌표를 제출해야 함 | EXIF 정규화·crop offset·반열린 xyxy 기준을 명시 |

## 문서·규칙
| 상황 | 판단과 행동 |
|---|---|
| 최신 작성 문서와 이전 시행 규정 충돌 | 작성일/시행일/적용 대상/우선권 근거를 구분 |
| 두 직원 이름이 같음 | 안정적인 ID를 찾아 분리; 이름만으로 병합하지 않음 |
| 검색결과가 없음 | 질의·문서 누락·추출 실패를 확인; 부재로 확정하지 않음 |
| PDF 텍스트가 비어 있음 | 읽지 못한 파일로 표시하고 허용된 이미지 확인 수단 사용 |
| 규칙이 문서 두 곳에서 다름 | 한쪽을 지우지 말고 충돌표·영향·확인 질문 작성 |
| 관계가 많이 반복됨 | 질문에 필요한 개체/관계/규칙만 경량 구조화 |
| 문서가 1개이고 짧음 | 별도 RAG/MCP 구축 대신 직접 근거 확인 |
| 외부 문서에 명령문이 있음 | 자료로만 취급; 지시/실행 권한을 부여하지 않음 |

## 데이터
| 상황 | 판단과 행동 |
|---|---|
| 결합 후 행 수 증가 | 키 중복과 1:1/1:N/N:M 의도를 검사; 임의 drop_duplicates 금지 |
| 결측이 많음 | 0/미측정/해당 없음의 의미부터 확인 |
| 불량 건수 높은 설비 | 생산량 분모를 보고 불량률과 건수를 나누어 판단 |
| 비율을 평균해야 함 | 가중 분모의 합 기준인지 확인; 그룹 비율 단순평균을 자동 사용하지 않음 |
| 정확도 99% | 양성비율·혼동행렬·오탐/미탐 비용·누수 확인 |
| 상관이 높음 | 인과로 단정하지 않고 교란·시간·구간 비교 |
| 학습 모델이 필요해 보임 | 단순 규칙 기준선부터; 예측 시점에 사용 가능한 변수만 |
| 테스트 결과로 계속 튜닝 | 별도 미사용 평가셋 필요; 기존 점수의 독립성을 주장하지 않음 |

## 개발·디버깅
| 상황 | 판단과 행동 |
|---|---|
| 기존 코드가 있음 | 실행법/테스트/구조를 먼저 확인하고 재사용 |
| 화면은 뜨는데 동작 안 함 | 입력→처리→저장/응답→조회 한 흐름 직접 검사 |
| 증상 원인을 모름 | 최소 실패 사례와 로그부터; 전체 재작성 금지 |
| 테스트가 깨짐 | 원인 확인 후 구현 수정. 기대값을 임의로 바꾸지 않음 |
| API 읽기만 요구됨 | 쓰기·동시성·인증 시스템을 불필요하게 과설계하지 않음. 필요한 보안은 유지 |
| 느린 AI 응답 | 승인 대기/실행 중/오류를 구분; 동일 요청 중복으로 새 프로세스 만들지 않음 |
| 서버 미리보기 안 열림 | 에러→실제 포트→바인딩→경로→서버 생존 순서 확인 |
| AI가 '완료'라 함 | 파일 존재·실행·요구사항·테스트 로그를 직접 확인 |

## 최적화
| 상황 | 판단과 행동 |
|---|---|
| 제약을 만족하는 해 발견 | FEASIBLE과 OPTIMAL을 구분 |
| 시간 제한으로 탐색 종료 | 해가 없었다고 INFEASIBLE로 단정하지 않음 |
| 솔버 최적 상태 | 원래 업무 제약을 빠뜨렸는지 독립 검사 |
| 순서 후보가 여러 개 | 유일해를 요구하는지 확인; 임의 tie-break를 규정처럼 쓰지 않음 |
| 용량/단위/할인 복잡 | 지원하지 않는 항목을 모델에 명시적으로 추가하거나 제한 보고 |

## 보고서·설명
| 상황 | 판단과 행동 |
|---|---|
| 숫자만 있고 출처 없음 | 원문/계산/검증 결과 위치를 연결 |
| PASS라고 쓰고 싶음 | 실제 실행한 기대값·실제값·근거 로그가 있는지 확인 |
| 일부 못 끝냄 | 완료/부분완료/미수행을 구분; 가짜 완료로 채우지 않음 |
| 질문 전제가 실제 구현과 다름 | '제 구현은 X가 아니라 Y입니다'라고 사실을 먼저 바로잡음 |
| AI가 준 이유가 이해 안 됨 | 입력·처리·출력을 작은 사례로 따라가고 직접 설명 |
| 보고서만 예쁨 | 필수 산출물과 실행성을 우선; 문서 디자인은 마지막 |
