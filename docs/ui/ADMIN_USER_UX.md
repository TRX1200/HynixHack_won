# 운영자 업무와 사용자 목표 구별하기

역할 이름부터 UI를 추측하지 않는다. 실제로 누가 어떤 기록을 보고 어떤 행동을 완료해야 하는지 확인한다. 기존 서비스의 역할·권한·동작 규칙이 우선이다.

| 맥락 | 먼저 드러낼 정보 | 기본 흐름 |
| --- | --- | --- |
| 운영자 | 처리 대상, 상태, 우선순위, 실패 이유 | 검색·필터→목록→상세→작업 결과 |
| 일반 사용자 | 내 목표, 필요한 입력, 진행·결과 | 입력→확인→제출→결과 또는 내 기록 |
| 읽기 전용 사용자 | 볼 수 있는 자료와 범위 | 목록→상세; 수정 동작은 권한에 맞게 처리 |

운영자 화면은 한눈에 비교할 수 있는 표와 명확한 행 동작이 유용할 수 있다. 일반 사용자 화면은 주요 행동 하나와 필요한 정보에 집중한다. 어느 경우든 모든 내용을 카드나 KPI로 바꾸지 않는다.

## 작업을 완료할 수 있게 만들기

- 검색·필터·정렬은 현재 적용 상태를 보이고 초기화 경로를 둔다. 많은 기록에서는 전체를 한꺼번에 렌더링하지 않는 기존 방식을 유지한다.
- 대량 작업은 선택 건수와 적용 범위를 보여준다. 되돌릴 수 없는 동작은 대상과 결과를 확인하게 하고, 실제 지원하지 않는 복구를 약속하지 않는다.
- 폼에는 보이는 라벨, 필수 조건, 입력별 오류를 둔다. 실패 뒤 수정 가능한 입력을 보존하고 중복 제출을 방지한다.
- 저장 완료는 서버 응답과 실제 결과를 확인한 뒤 표시한다. 버튼 클릭만으로 성공 메시지를 만들지 않는다.
- 빈 목록·불러오는 중·실패·권한 부족을 서로 다른 상태로 보여준다. 필요하면 다시 시도하거나 이전 위치로 돌아갈 경로를 둔다.

## 화면과 실제 권한을 함께 검증

버튼 숨김·disabled·역할 선택 UI는 서버 권한 검증을 대신하지 않는다. 서버가 인증된 사용자와 대상 기록의 권한을 확인해야 한다. 요구사항에 맞게 비로그인, 허용 역할, 금지 역할, 다른 사용자의 기록 접근을 확인한다. 허용된 로컬 테스트 방식으로 직접 요청했을 때도 금지 작업이 거절되어야 한다.

권한 테스트 결과와 화면 검토 결과를 따로 남긴다. UI에서 버튼이 없어도 요청이 성공하면 권한 검증은 FAIL이다. 서버 기능이나 테스트 수단이 없으면 NOT_RUN 또는 BLOCKED로 기록하고, mock UI나 데모로 대체하여 PASS라 하지 않는다. 실제 사용자·운영 데이터 대신 허용된 로컬 합성 fixture를 사용한다.

처음에는 [디자인 기본값](DESIGN_SYSTEM.md)과 이 문서만 읽는다. 좁은 화면에서 복잡한 목록이 깨지면 [반응형](RESPONSIVE.md)을 추가하고, 완료 시 [시각 검토](VISUAL_REVIEW.md)를 진행한다.
